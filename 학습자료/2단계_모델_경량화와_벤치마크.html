2단계 해설 — 모델 경량화와 벤치마크

1왜 경량화하는가 — "서빙"의 관점

학습(training)은 한 번이지만 추론(inference)은 리뷰가 등록될 때마다 일어납니다. 서빙에서 중요한 건 세 가지:

관심사왜 중요한가경량화의 기여
모델 크기Docker 이미지 크기, 메모리, 콜드 스타트(Cloud Run이 0→1로 깰 때 로드 시간)54MB → 14MB
추론 속도사용자가 리뷰 제출 후 기다리는 시간환경에 따라 다름 (§4 실측!)
의존성 크기PyTorch 전체(수 GB)를 서버에 설치할 것인가?onnxruntime만으로 추론 가능
우리가 모델 선택 단계에서 이미 14M 파라미터 small 모델을 고른 것이 1차 경량화였습니다. 2차가 이번 단계(포맷·정밀도 최적화)입니다. 경량화는 "기법 적용"이 아니라 서빙 비용을 낮추는 의사결정의 연속입니다.

2ONNX 변환 — 모델을 "실행 계획서"로 바꾸기

ONNX는 프레임워크 중립적인 계산 그래프 포맷입니다. PyTorch 모델은 "파이썬 코드 + 가중치"지만, ONNX는 "연산 순서도 + 가중치"라서 파이썬/PyTorch 없이도 어떤 런타임이든 실행할 수 있습니다.

# export_onnx.py 핵심
model.eval()                          # ① Dropout 등 학습 전용 동작 고정 — 변환 전 필수
dummy = tokenizer("이 영화 정말 재미있어요", return_tensors="pt")   # ② 더미 입력
torch.onnx.export(
    LogitsOnly(model), (...),         # ③ dict 대신 logits만 반환하는 래퍼
    dynamic_axes={"input_ids": {0: "batch", 1: "seq"}, ...},      # ④ 가변 축
    opset_version=17,                 # ⑤ 연산 규격 버전 명시
)
  • ① eval(): 안 하면 Dropout이 켜진 채 그래프에 박제되어 추론 결과가 매번 달라집니다.
  • ② 더미 입력: 변환기는 코드를 읽는 게 아니라 실제로 한 번 실행하면서 지나간 연산을 기록(트레이싱)합니다. 그래서 실제 입력과 같은 구조의 예시가 필요합니다.
  • ④ dynamic_axes: 트레이싱은 "그때 지나간 크기"를 고정해버립니다. 배치·문장길이 축을 가변으로 선언하지 않으면 더미와 같은 길이의 리뷰만 처리되는 모델이 됩니다.
한글 경로 함정 (실전 디버깅) — 양자화 도구 내부의 C++ 파일 IO가 미션 18 같은 한글 경로를 처리하지 못해 FileNotFoundError가 났습니다. ASCII 임시 폴더에서 양자화 후 결과만 복사해오는 방식으로 우회했습니다. Windows + 한글 폴더 조합에서 자주 만나는 유형의 문제입니다.

3동적 양자화 — FP32를 INT8로

모델 가중치는 기본 32비트 실수(FP32)입니다. 동적 양자화는 가중치를 8비트 정수(INT8)로 바꿔 저장하고, 활성값(레이어 중간 출력)의 변환 범위는 추론 시점에 즉석 계산합니다.

quantize_dynamic("fp32.onnx", "int8.onnx", weight_type=QuantType.QInt8)
# 결과: 54.1 MB → 14.0 MB (정확히 이론값 ~1/4)
32bit → 8bit이니 크기가 ¼이 되는 건 당연한데, 왜 "추가 학습 없이"도 정확도가 유지될까? Transformer의 연산 대부분은 Linear(행렬곱) 레이어이고, 행렬곱은 반올림 오차가 평균적으로 상쇄되는 성질이 있어 INT8 근사에 관대합니다. 우리 실측에서도 검증 문장 16개 전부 FP32와 판정 일치(100%)했습니다. 만약 정확도가 무너졌다면 다음 카드는 QAT(학습하며 양자화 오차 보정)였지만, 필요 없었습니다.

4벤치마크 — 그리고 "성능 역전"의 목격

측정 설계 (교재 원칙 그대로):

  • 워밍업 10회 — 첫 실행엔 커널 로드·캐시 채우기 오버헤드가 섞이므로 버립니다.
  • 본측정 100회 — 1회 측정은 우연입니다. 분포를 봐야 합니다.
  • 평균±표준편차 + P99 — 평균만 보면 "가장 느린 1%의 사용자"를 놓칩니다. SLA는 P99로 잡습니다.
  • E2E 측정 — 토크나이즈→추론→softmax 전 구간. 순수 연산만 재면 실제 API 체감과 다릅니다.

실측 결과 (이 PC, CPU, 2회 실행 재현 확인):

엔진평균(ms)표준편차P99(ms)정확도크기(MB)
PyTorch FP3227.63.839.5100%53.9
ONNX FP3249.710.976.2100%54.1
ONNX INT845.817.789.7100%14.0
교재는 "ONNX 변환은 보통 ~2배 빨라진다"고 했지만, 이 환경에선 PyTorch가 오히려 1.8배 빠릅니다. 교재의 다른 경고 — "INT8 하드웨어 가속을 지원하지 못하면 변환·복원 오버헤드로 오히려 느려지는 성능 역전이 발생한다. 반드시 실측하라" — 가 정확히 들어맞은 사례입니다. 원인 가설: ① 최신 PyTorch의 CPU 어텐션 커널(SDPA)이 이미 고도로 최적화됨 ② 트레이싱 변환 과정에서 어텐션이 잘게 쪼개진 연산들로 풀려 그래프 최적화 이득이 상쇄됨 ③ 이 CPU에서 INT8 행렬곱 가속(VNNI 등) 이득보다 동적 양자화의 즉석 범위 계산 오버헤드가 큼. "측정 없이 믿지 마라"가 이 단계의 진짜 교훈입니다.

5의사결정 — 그럼 뭘로 서빙하나?

속도만 보면 PyTorch인데, 왜 최종 선택은 ONNX INT8일까요? 서빙의 총비용으로 비교합니다:

기준PyTorch 서빙ONNX INT8 서빙
추론 의존성torch 전체 (~2GB+)onnxruntime (~수십 MB)
Docker 이미지수 GB수백 MB
모델 파일54 MB14 MB
콜드 스타트(Cloud Run)느림 (이미지 풀링+로드)빠름
레이턴시~28ms~46ms
정확도100%100% (판정 완전 일치)
리뷰 등록당 1회 추론에서 28ms vs 46ms는 사용자가 감지할 수 없는 차이지만, Docker 이미지 수 GB vs 수백 MB는 배포 시간·콜드 스타트·비용에 직결됩니다. 손해보는 지표(레이턴시 +18ms)가 서비스 요구사항 안이고, 이득(배포 footprint)이 크므로 ONNX INT8 채택. 단, 배포 대상(Cloud Run)의 CPU는 이 PC와 다르므로 순위가 바뀔 수 있다는 한계를 보고서에 명시합니다 — 이것도 교재의 "실행 하드웨어에서 사전 측정하라" 원칙입니다.

6셀프 체크

Q1. ONNX 변환 전 model.eval()을 빼먹으면 어떤 문제가 생기나?

Dropout 같은 학습 전용 동작이 켜진 채 그래프에 고정되어, 서빙 시 같은 입력에도 결과가 흔들리거나 성능이 저하된다.

Q2. dynamic_axes를 지정하지 않으면 어떤 모델이 만들어지나?

더미 입력과 동일한 배치·문장 길이만 받는 모델. 트레이싱은 "지나간 크기"를 상수로 박제하기 때문에, 가변으로 쓸 축은 명시적으로 선언해야 한다.

Q3. 동적 양자화에서 "동적"은 무엇이 동적이라는 뜻인가?

가중치는 미리(정적으로) INT8로 저장하지만, 활성값의 양자화 범위(scale)는 추론 시점에 입력마다 즉석에서 계산한다는 뜻. 그래서 사전 캘리브레이션 데이터가 필요 없다.

Q4. 우리 실측에서 INT8이 FP32(PyTorch)보다 느렸는데, 그래도 INT8을 채택한 근거는?

레이턴시 차이(+18ms)는 사용자 요구사항 내인 반면, torch 의존성 제거(이미지 수 GB→수백 MB)·모델 ¼ 크기·콜드 스타트 단축이라는 배포 이득이 훨씬 크고, 정확도 손실은 0이기 때문. 속도 단일 지표가 아니라 서빙 총비용으로 결정했다.

Q5. 워밍업을 버리고, 평균이 아닌 P99를 보는 이유는?

첫 실행엔 초기화 오버헤드가 섞여 통계를 오염시키고, 평균은 꼬리(가장 느린 요청들)를 숨긴다. 서비스 품질 약속(SLA)은 "거의 모든 사용자"가 겪는 P99로 정해야 안전하다.
