4단계 해설 — Streamlit 프론트엔드

이번 단계에서 만든 것: 4개 페이지(영화 목록·영화 추가·리뷰 등록·최근 리뷰)로 구성된 Streamlit 앱. 모든 데이터는 백엔드 API로만 읽고 씁니다(미션 제약). 그리고 이 단계 검증 중에 백엔드 기동 48초 → 4.8초라는 큰 개선을 얻었습니다.

1Streamlit의 실행 모델 — "전부 다시 실행"

Streamlit의 대원칙: 사용자가 위젯을 건드릴 때마다 스크립트 전체가 위에서 아래로 다시 실행됩니다. 이 단순한 모델이 모든 설계 결정의 출발점입니다.

재실행 모델의 결과우리의 대응
입력 필드 하나 바뀔 때마다 재실행 → API 폭격st.form으로 묶어 제출 버튼까지 재실행 차단
재실행마다 영화 목록 API 재호출@st.cache_data(ttl=30)로 30초 재사용
백엔드가 죽어 있으면 페이지마다 다른 에러페이지 최상단 require_backend() + st.stop()
우리 앱은 폼 제출 결과를 즉시 API로 보내고 응답을 표시할 뿐, 재실행 사이에 유지할 자체 상태가 없어서 st.session_state는 쓰지 않았습니다. 교재의 도구는 "필요할 때" 꺼내는 것 — 상태가 없는데 상태 관리 코드를 넣는 건 복잡도만 추가합니다.

2st.form — 재실행 폭주 막기

# pages/2_리뷰_등록.py
with st.form("review_form"):
    movie = st.selectbox("영화 선택 *", movies, format_func=...)
    author = st.text_input("작성자 이름 *")
    content = st.text_area("리뷰 내용 *")
    submitted = st.form_submit_button("리뷰 등록")   # ← 이때만 재실행

if submitted:
    with st.spinner("감성 분석 중..."):
        review = api_client.create_review({...})
    st.markdown(f"### AI 감성 분석 결과: {sentiment_badge(...)}")
form이 없으면 selectbox 선택→재실행, 이름 한 글자→재실행... 입력 도중에 계속 스크립트가 돕니다. form 안의 위젯은 제출 버튼을 누를 때까지 재실행을 트리거하지 않으므로, API 호출은 정확히 사용자가 의도한 1회만 발생합니다. st.spinner는 감성 분석(~50ms+네트워크) 동안 "일하고 있음"을 보여주는 최소한의 UX입니다.

3캐싱 전략 — ttl과 명시적 무효화의 조합

# lib/api_client.py
@st.cache_data(ttl=30)              # 같은 인자의 호출은 30초간 재사용
def list_movies() -> list[dict]: ...

def create_movie(payload) -> dict:
    r = requests.post(...)
    st.cache_data.clear()           # 쓰기 성공 → 캐시 즉시 무효화
    return r.json()
읽기(ttl=30)는 "약간 오래된 데이터 허용"으로 API 호출을 줄이고, 쓰기 직후엔 clear()로 내가 등록한 영화가 바로 목록에 보이게 합니다. 이 조합이 없으면 둘 중 하나를 잃습니다 — 캐시가 없으면 재실행마다 API 호출, 무효화가 없으면 "등록했는데 안 보여요" 버그.

st.cache_resource를 안 쓴 이유: 그건 모델·DB 연결처럼 메모리 상주 객체용인데, 우리 모델은 백엔드에 있습니다. 프론트가 주고받는 건 전부 JSON(순수 데이터) → cache_data가 맞는 도구입니다.

4연결 확인과 빈 상태 — 교재의 UX 원칙

def require_backend():
    try:
        health = requests.get(f"{BACKEND_URL}/health", timeout=5).json()
    except requests.RequestException:
        st.error("백엔드에 연결할 수 없습니다. ...")
        st.stop()                    # ← 이하 렌더링 완전 중단
    if not health.get("model_loaded"):
        st.warning("모델이 아직 로드되지 않았습니다."); st.stop()
  • st.stop() 패턴: 전제조건(백엔드 연결)이 깨지면 반쪽짜리 화면 대신 명확한 안내 한 줄로 끝냅니다. 3단계에서 만든 /health의 model_loaded가 여기서 쓰입니다 — "서버는 떴지만 모델이 아직"인 상태까지 구분.
  • 빈 상태(Empty State): 영화 0개면 빈 화면이 아니라 "영화 추가 페이지에서 첫 영화를 등록해보세요!" 안내를 보여줍니다. 리뷰 0개도 동일. 사용자가 다음 행동을 알 수 있게.
  • 에러 전달: 백엔드 422 응답의 detail을 그대로 st.error로 노출 — 프론트에서 검증 로직을 중복 구현하지 않고 백엔드(신뢰의 경계)의 판단을 전달만 합니다.

6실전 개선 — 백엔드 기동 48초 → 4.8초

4단계 테스트 준비 중 백엔드가 80초 대기에도 안 떠서 실패했습니다. "왜 이렇게 느리지?"를 측정으로 추적한 결과:
onnxruntime import: 0.4s
transformers import: 4.9s      ← 서빙엔 안 쓰는 기능까지 통째로
AutoTokenizer load: 10.4s      ← (콜드 상태에선 백신 스캔까지 겹쳐 수십 초)
tokenizers import + load: 0.1s ← 같은 tokenizer.json을 읽는 경량 라이브러리

토크나이저의 실체는 tokenizer.json 파일이고, AutoTokenizer(transformers)는 그걸 읽는 무거운 껍데기였습니다. 경량 tokenizers 라이브러리로 직접 읽도록 교체하면서 토큰 ID가 완전히 동일함을 검증했습니다 ([2, 9380, 9611, 10561, 3] == 동일).

전 (AutoTokenizer)후 (tokenizers)
서버 기동48~80초4.8초
서빙 의존성transformers 전체tokenizers만 (Docker 이미지 추가 절감)
토큰화 결과완전 동일 (실측 검증)
2단계의 교훈("측정 없이 믿지 마라")이 여기서도 반복됩니다: "느리다" 다음에 온 것은 추측이 아니라 임포트별 시간 측정이었고, 병목이 확정되자 해법은 자명했습니다. 이 개선은 5단계 Docker 이미지 크기와 Cloud Run 콜드 스타트에 그대로 이어집니다.

8왓챠피디아풍 UI — unsafe_allow_html과 XSS 방어

영화 목록을 "박스형 카드"에서 왓챠피디아처럼 다크 테마 + 6열 포스터 그리드 + 빨간 별점으로 개편했습니다.

요소구현
다크 테마config.toml의 [theme] base="dark" + 포인트 컬러 #ff2f6e — CSS 없이 앱 전체 적용
균일한 포스터st.image는 원본 비율대로 높이가 제각각 → HTML <img>에 aspect-ratio:2/3; object-fit:cover로 영화 포스터 표준 비율 고정. 깨진 URL은 onerror로 대체 이미지
별점긍정 확률 평균×5를 평균★4.2 형태의 빨간 텍스트로 — 왓챠의 "예상★" 문법 차용
HTML 카드는 st.markdown(..., unsafe_allow_html=True)로 렌더링하는데, 교재의 경고 그대로 사용자 입력을 그대로 끼워 넣으면 XSS에 뚫립니다. 영화 제목은 누구나 입력하는 값 — 제목에 <script>alert(1)</script>를 넣으면 모든 방문자의 브라우저에서 실행될 수 있습니다. 그래서 템플릿은 개발자 고정 문자열로 유지하고, 제목·감독·URL 등 사용자 유래 값은 전부 html.escape()를 거칩니다. 테스트(1-1)가 실제로 악성 제목을 등록해 &lt;script&gt;로 이스케이프되는지 자동 검증합니다.
테스트 수정 중 배운 것 하나: XSS 테스트가 처음에 실패했는데, 원인은 이스케이프 누락이 아니라 캐시였습니다. 악성 영화를 requests로 직접 등록하니 api_client.create_movie()의 캐시 무효화가 우회되어, 화면엔 30초 전 목록이 그대로 나온 것. "등록은 반드시 api_client를 통해서"라는 단일 창구 규칙이 캐시 정합성의 전제라는 걸 테스트가 증명해준 셈입니다.

9셀프 체크

Q1. st.form 없이 리뷰 등록 페이지를 만들면 어떤 문제가 생기나?

selectbox 선택, 이름 입력 등 위젯 조작마다 스크립트가 재실행된다. 입력 도중 불필요한 재실행이 반복되고, 최악의 경우 미완성 입력으로 API가 호출될 수 있다. form은 제출 버튼까지 재실행을 차단한다.

Q2. 캐시 ttl=30만 있고 st.cache_data.clear()가 없으면 어떤 버그가 보이나?

영화를 등록해도 최대 30초 동안 목록에 안 나타난다("등록했는데 안 보여요"). 쓰기 성공 직후 명시적으로 캐시를 비워야 읽기 캐시와 쓰기가 정합해진다.

Q3. 프론트에서 st.cache_resource를 쓸 일이 없는 이유는?

cache_resource는 모델 세션·DB 연결 같은 메모리 상주 공유 객체용인데, 우리 구조에선 그런 무거운 객체가 전부 백엔드에 있다. 프론트가 다루는 건 API가 준 JSON(순수 데이터)뿐이라 cache_data가 맞다.

Q4. BACKEND_URL을 코드에 하드코딩하지 않고 st.secrets로 읽는 이유는?

로컬(localhost:8000)과 배포(실제 서버 주소)에서 값이 달라지는 설정이기 때문. secrets로 분리하면 코드 수정 없이 환경별로 값만 바꾸면 되고, 민감한 주소가 Git에 남지 않는다.

Q5. AutoTokenizer→tokenizers 교체가 안전하다고 확신한 근거는?

두 방식 모두 같은 tokenizer.json을 읽으며, 같은 입력 문장에 대한 토큰 ID 배열이 완전히 일치함을 실측으로 확인했다. 교체 후 3단계 통합 테스트(감성 판정 포함)도 전부 통과했다.
