3단계 해설 — 리뷰 API와 감성분석 연동

이번 단계에서 만든 것: 2단계의 INT8 모델을 백엔드에 탑재했습니다. 서버 기동 시 모델을 1회 로드(lifespan)하고, 리뷰가 등록되면 자동으로 감성 분석이 실행되어 결과가 DB에 저장됩니다. 이번 단계의 백미는 async와 스레드의 관계 — 실제 버그로 배웠습니다.

backend/app/
├── ml/
│   ├── loader.py       ← ModelManager (세션·토크나이저 보관, lifespan에서 load)
│   └── predictor.py    ← predict(text) → 긍정확률 (순수 동기 함수)
├── routers/reviews.py  ← POST(감성분석) · GET · /recent · DELETE
├── services/review_service.py
├── schemas.py          ← + SentimentLabel(Enum), ReviewCreate/Response
└── main.py             ← lifespan에서 모델 load/unload, health에 실제 상태

1모델 생명주기 — lifespan에서 딱 1회

# main.py
@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()
    model_manager.load(settings.model_path)   # ← 기동 시 1회 (~1초)
    yield                                     # ← 서버 가동 중
    model_manager.unload()                    # ← 종료 시 해제
모델 로드는 디스크 IO + 메모리 할당이 큰 무거운 연산입니다. 요청마다 로드하면 리뷰 1건에 1초씩 걸리는 서비스가 됩니다. lifespan은 "서버 켤 때 1번"을 구조적으로 보장하는 자리 — 1단계에서 미리 만들어둔 그 자리에 모델이 들어왔습니다. /health가 model_loaded: true를 반환하는지로 로드 완료를 확인할 수 있고, 이건 나중에 Docker HEALTHCHECK의 근거가 됩니다.

ModelManager는 세션·토크나이저라는 상태를 갖는 클래스로 캡슐화했고, 앱 전체에서 인스턴스 하나(model_manager)만 씁니다. 전역 변수 두 개를 흩어두는 것보다 "로드됐나?"(loaded) 같은 질문에 한 곳에서 답할 수 있습니다.

2run_in_threadpool — async의 함정 피하기

FastAPI의 이벤트 루프는 싱글 스레드입니다. async def 안에서 오래 걸리는 동기 연산(ONNX 추론 = CPU 집약)을 그냥 호출하면, 그 연산이 끝날 때까지 루프가 멈춰 다른 모든 요청이 정지합니다.

# routers/reviews.py
@router.post("", ...)
async def create_review(body: ReviewCreate, conn = Depends(get_db)):
    ...
    # ❌ score = predictor.predict(body.content)        # 루프 블로킹!
    # ✅ 스레드 풀에 위임하고, 그동안 루프는 다른 요청 처리
    score = await run_in_threadpool(predictor.predict, body.content)
    label = "positive" if score >= 0.5 else "negative"
    return review_service.create_review(conn, body.model_dump(), label, score)
우리 추론은 ~46ms지만, 리뷰 10개가 동시에 들어오면 블로킹 방식에선 마지막 사용자가 460ms를 기다립니다(전부 직렬). run_in_threadpool은 추론을 백그라운드 스레드로 보내고 await로 결과만 기다리므로, 루프는 그동안 영화 목록 조회 같은 다른 요청을 계속 처리합니다. 대안은 엔드포인트를 일반 def로 선언하는 것(FastAPI가 통째로 스레드풀에서 실행)이지만, "어떤 연산이 무거운지"를 코드에 명시하는 지금 방식이 의도가 드러납니다.

3실전 버그 — "다른 스레드에서 만든 SQLite 객체"

테스트 첫 실행에서 터졌습니다: sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread. 1단계의 영화 API는 멀쩡했는데 왜 리뷰 API에서만?

원인은 sync/async의 실행 위치 차이입니다:

구성요소실행 스레드
sync 의존성 get_db()스레드풀의 스레드 A에서 연결 생성
sync 엔드포인트 (영화 API, def)스레드풀 — 연결과 같은 맥락 → 문제없음
async 엔드포인트 (리뷰 API, async def)이벤트 루프 스레드 B에서 연결 사용 → 💥

SQLite는 기본값으로 "연결은 만든 스레드에서만 써라"를 강제하는데, async 엔드포인트가 생기면서 같은 요청 안에서도 만든 스레드 ≠ 쓰는 스레드가 된 겁니다.

# database.py 수정
conn = sqlite3.connect(settings.db_path, check_same_thread=False)
이 완화가 안전한 이유가 중요합니다: 위험한 건 "여러 스레드가 동시에 한 연결 사용"인데, 우리 연결은 요청 하나에 속해 순차적으로만 쓰입니다(스레드가 바뀔 뿐 겹치지 않음). 교재의 "check_same_thread=False가 필요하다"는 문장을 1단계에선 "우린 요청당 연결이라 해당 없음"이라고 넘겼다가, async가 등장하자 정확히 그 상황이 재현됐습니다. 교재의 경고는 조건이 갖춰지면 반드시 온다 — 이번 단계 두 번째 교훈.

4감성 분석 파이프라인 — 텍스트가 점수가 되기까지

# ml/predictor.py
enc = tokenizer(text, truncation=True, max_length=256)   # ① 텍스트 → 토큰 ID
logits = session.run(None, {...})[0][0]                  # ② ONNX 추론 → [부정, 긍정] 점수
exp = np.exp(logits - logits.max())                      # ③ softmax (오버플로 방지)
score = (exp / exp.sum())[1]                             # ④ 긍정 확률 0~1
  • ① truncation=256: 아무리 긴 리뷰도 256토큰에서 자릅니다. 감성은 보통 앞부분에서 충분히 드러나고, 입력 길이를 묶어야 최악 레이턴시도 묶입니다.
  • ③ logits.max()를 빼는 이유: exp(큰 수)는 무한대로 넘칩니다. 최댓값을 빼도 softmax 결과는 수학적으로 동일(비율만 중요)하면서 오버플로가 방지됩니다.
  • ④ 확률을 그대로 저장: 라벨("positive")만 저장하면 "0.51 긍정"과 "0.99 긍정"이 구별 안 됩니다. 확률을 저장해두면 평균 평점(F-09)의 원천값이 되고, 라벨은 score ≥ 0.5로 파생됩니다.

실측: 긍정문 0.986 / 부정문 0.001 — 판정 경계(0.5)에서 멀리 떨어진 확신 있는 분포를 보입니다.

7셀프 체크

Q1. 모델 로드를 lifespan이 아니라 predict() 안에서 하면 어떤 일이 생기나?

리뷰 등록마다 디스크에서 모델을 다시 읽어 요청당 1초 이상 걸린다. lifespan은 "기동 시 1회 로드"를 구조적으로 보장한다.

Q2. async def 엔드포인트에서 predictor.predict()를 직접 호출하면?

이벤트 루프(싱글 스레드)가 추론 46ms 동안 멈춰 그 사이 도착한 모든 요청이 대기한다. run_in_threadpool로 위임해야 루프가 계속 다른 요청을 처리한다.

Q3. 이번 스레드 에러가 영화 API에선 안 나고 리뷰 API에서만 난 이유는?

영화 엔드포인트는 sync(def)라 의존성과 같은 스레드풀 맥락에서 실행되지만, 리뷰 엔드포인트는 async라 본문이 이벤트 루프 스레드에서 실행된다. 연결을 만든 스레드(풀)와 쓰는 스레드(루프)가 달라져 SQLite 기본 제약에 걸렸다.

Q4. check_same_thread=False가 우리 구조에서 안전한 근거는?

연결이 요청 하나에만 속하고, 요청 안에서는 순차적으로만 사용된다(동시 접근 없음). 위험한 것은 여러 스레드의 "동시" 사용이지 "이동"이 아니다.

Q5. 라벨 대신 확률(sentiment_score)을 DB에 저장하는 이유는?

확률이 원천 데이터고 라벨은 파생값(≥0.5)이기 때문. 확률이 있어야 평균 평점을 계산할 수 있고, 필요하면 임계값을 바꿔 라벨을 재계산할 수도 있다. 반대 방향(라벨→확률)은 불가능하다.
