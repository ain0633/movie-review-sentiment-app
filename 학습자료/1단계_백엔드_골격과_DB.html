1계층 분리 — 요청이 흐르는 길

요청 하나가 처리되는 경로를 따라가 보면 각 파일의 역할이 보입니다.

POST /movies (JSON)
   ↓
schemas.py   MovieCreate가 입력 검증 (틀리면 여기서 422로 끝)
   ↓
routers/movies.py   HTTP 껍데기: URL·상태코드 결정, DB 연결 주입받음
   ↓
services/movie_service.py   실제 일: INSERT 실행, 결과 반환
   ↓
schemas.py   MovieResponse가 응답 형태 보장 → JSON 반환
라우터는 "HTTP를 아는 층", 서비스는 "일을 하는 층"으로 나눴습니다. 서비스 계층은 FastAPI를 전혀 import하지 않는 순수 Python이라, 나중에 프레임워크를 바꾸거나 스크립트에서 재사용해도 그대로 씁니다. 의존 방향은 항상 routers → schemas / services 한쪽으로만 흐릅니다(단일 책임 원칙).

2Pydantic 스키마 — 신뢰의 경계

외부에서 오는 데이터는 전부 의심 대상입니다. Pydantic 모델이 앱의 입구에서 방어벽 역할을 합니다.

# schemas.py
class MovieCreate(BaseModel):                      # 요청 = 입력 방어
    title: str = Field(min_length=1, max_length=200)
    release_date: date                             # "2010-07-21" → date로 자동 파싱
    poster_url: HttpUrl                            # URL 형식 아니면 거부

class MovieResponse(BaseModel):                    # 응답 = 출력 계약
    avg_score: float | None = Field(default=None, ge=0.0, le=1.0)
    ...

검증 실패 시 내가 아무 코드도 안 써도 FastAPI가 자동으로 422 Unprocessable Entity와 "어느 필드가 왜 틀렸는지"를 JSON으로 응답합니다. 스모크 테스트에서 빈 제목과 "낫유알엘" URL이 422로 거부되는 걸 확인했습니다.

요청과 응답 스키마를 따로 만든 이유: 요청은 "한계 검증"(길이·형식), 응답은 "계약"(클라이언트가 믿고 쓸 필드 목록)으로 역할이 다릅니다. 응답에 response_model을 명시하면 스키마에 없는 필드는 자동 필터링돼 내부 정보 유출도 막고, /docs 자동 문서에도 그대로 반영됩니다(→ 보고서의 "FastAPI Docs 캡처" 제출물).

3의존성 주입 — Depends(get_db)

모든 엔드포인트가 DB 연결이 필요합니다. 함수 안에서 매번 sqlite3.connect(...)를 쓰는 대신, FastAPI에게 "이 함수는 DB 연결이 필요해"라고 선언만 합니다.

# database.py
def get_db():
    conn = sqlite3.connect(settings.db_path)
    conn.row_factory = sqlite3.Row        # 컬럼명으로 접근: row["title"]
    conn.execute("PRAGMA foreign_keys = ON")
    try:
        yield conn                        # ← 여기서 엔드포인트가 실행됨
    finally:
        conn.close()                      # 응답 후 반드시 정리

# routers/movies.py
def list_movies(conn: sqlite3.Connection = Depends(get_db)):
    return movie_service.list_movies(conn)

yield 앞은 요청 전 준비, 뒤는 요청 후 정리 — 파이썬 with문과 같은 구조입니다.

① 연결 생성/종료 코드 중복 제거 ② 테스트에서 가짜 DB로 갈아끼우기(dependency_overrides) 가능 ③ 연결이 요청 하나에만 속하므로 동시 쓰기 충돌을 직접 관리할 필요가 없습니다.
3단계에서 실제로 밟은 함정 (사후 수정) — 처음엔 "요청마다 새 연결이니 SQLite의 단일 스레드 제약과 무관하다"고 생각했는데, async 엔드포인트가 추가되자 SQLite objects created in a thread can only be used in that same thread 에러가 터졌습니다. sync 의존성(get_db)은 스레드풀에서, async 엔드포인트 본문은 이벤트 루프 스레드에서 실행되어 — 같은 요청 안에서도 스레드가 달라질 수 있기 때문입니다. 해결: sqlite3.connect(..., check_same_thread=False). 연결이 요청 하나에서만 순차적으로 쓰이므로 이 완화는 안전합니다. 교재가 말한 "check_same_thread=False가 필요하다"가 정확히 이 상황이었습니다.

4SQLite 설계 — 파라미터화 쿼리와 FK CASCADE

파라미터화 쿼리 — 사용자 입력이 들어가는 SQL은 반드시 ? 플레이스홀더:

# ✅ 안전 — 값이 "데이터"로만 취급됨
conn.execute("DELETE FROM movies WHERE id = ?", (movie_id,))

# ❌ 절대 금지 — SQL 인젝션
conn.execute(f"DELETE FROM movies WHERE id = {movie_id}")
f-string으로 SQL을 조립하면 입력에 1 OR 1=1 같은 문자열이 오는 순간 전체 테이블이 지워질 수 있습니다. 플레이스홀더는 드라이버가 값을 이스케이프해서 문법이 아닌 데이터로만 다룹니다.

FK CASCADE — 영화를 지우면 그 영화의 리뷰도 함께 지워져야 합니다(고아 레코드 방지):

movie_id INTEGER NOT NULL REFERENCES movies(id) ON DELETE CASCADE
SQLite는 FK 제약이 기본으로 꺼져 있습니다. 연결마다 PRAGMA foreign_keys = ON을 실행해야 CASCADE가 실제로 동작합니다 — 그래서 get_db() 안에 넣었습니다.

평균 평점은 컬럼이 아니라 쿼리:

SELECT m.*, AVG(r.sentiment_score) AS avg_score, COUNT(r.id) AS review_count
FROM movies m LEFT JOIN reviews r ON r.movie_id = m.id
GROUP BY m.id
평점을 movies 테이블 컬럼으로 저장하면 리뷰가 등록/삭제될 때마다 갱신해야 하고, 하나라도 빠뜨리면 데이터가 어긋납니다(정합성 문제). 조회 시점에 AVG()로 계산하면 어긋날 데이터 자체가 없습니다. LEFT JOIN이라 리뷰가 0개인 영화도 목록에 나오고, 그때 avg_score는 NULL(→ 응답에서 null)이 됩니다.

5main.py — lifespan과 CORS

@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()      # ← 서버 시작 시 1회: 테이블 생성
    yield          # ← 서버가 여기서 요청을 받으며 살아있음
                   # (yield 뒤 = 종료 시 정리 — 2단계에서 모델 해제 추가)
lifespan은 "서버 켤 때 한 번 / 끌 때 한 번"의 표준 자리입니다. 지금은 테이블 생성만 하지만, 2~3단계에서 감성 분석 모델 로드가 바로 이 자리에 들어갑니다 — 요청마다 모델을 로드하는 안티패턴을 구조적으로 차단하는 위치입니다.
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.allowed_origins,   # ["http://localhost:8501"]
    allow_methods=["GET", "POST", "DELETE"],
)
브라우저는 다른 출처(도메인)의 API 호출을 기본 차단합니다(동일 출처 정책). 우리 구조는 Streamlit(8501) → FastAPI(8000)로 출처가 다르므로 CORS 허용이 필요합니다. 이때 allow_origins=["*"]가 아니라 프론트 도메인만 명시하는 것이 학습자료의 보안 원칙 — 배포 시 Streamlit Cloud 주소로 교체합니다.

8셀프 체크 — 답을 보기 전에 스스로 답해보세요

Q1. 서비스 계층(movie_service.py)이 FastAPI를 import하지 않는 이유는?

비즈니스 로직을 프레임워크와 분리해 순수 Python으로 유지하기 위해서. 프레임워크가 바뀌어도, 스크립트·테스트에서 단독 호출해도 그대로 재사용할 수 있고, 의존 방향이 한쪽(routers→services)으로만 흘러 구조가 단순해진다.

Q2. 평균 평점을 movies 테이블의 컬럼으로 두지 않은 이유는?

리뷰 등록/삭제 때마다 컬럼을 갱신해야 해서 정합성이 깨질 위험이 생긴다. 조회 시 AVG() 집계로 계산하면 원본(리뷰)에서 항상 파생되므로 어긋날 수 없다.

Q3. PRAGMA foreign_keys = ON을 빼먹으면 어떤 버그가 생기나?

영화를 삭제해도 그 영화의 리뷰가 지워지지 않고 고아 레코드로 남는다(ON DELETE CASCADE가 무시됨). SQLite는 FK 제약이 기본 꺼져 있어 연결마다 켜야 한다.

Q4. 클라이언트가 잘못된 JSON(빈 제목)을 보내면 몇 번 상태코드가, 누구에 의해 반환되나?

422. 내가 작성한 코드가 아니라 FastAPI가 Pydantic 검증 실패를 감지해 자동으로 반환한다. 엔드포인트 함수는 실행조차 되지 않는다.

Q5. get_db()의 yield 앞/뒤 코드는 각각 언제 실행되나?

앞(연결 생성, PRAGMA)은 요청 처리 전, 뒤(finally의 conn.close())는 응답이 나간 후. 요청 하나의 생애주기를 감싸는 with문과 같은 구조다.
